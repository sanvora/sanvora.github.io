AI Chat Assistant

How it works

The chat widget on this site runs a fine-tuned 360M-parameter language model directly in your browser — no server involved. This page documents the architecture: how responses are generated, how context is retrieved, how the model was trained via knowledge distillation, and how a token-gated cloud path enables full-scale answers when needed.

Section 01

Runtime Flow

Every message travels through a retrieval pipeline before generation. Two inference paths exist: an on-device model for all visitors, and a cloud model activated by a signed access token.

On-Device Path

Default for all visitors. Inference runs inside the browser tab via WebGPU — no network call, no latency on the model request.

Cloud Path

Activated by a time-limited signed token. Routes to Llama 3.3 70B via Cloudflare. The API key never reaches the browser.

RAG Pipeline

Embeds the query, finds the closest chunks from the portfolio knowledge base by cosine similarity, and injects them as context before generation.

Section 02

Build Pipeline

Resume and company data is embedded and encrypted at CI time. Only ciphertext ships to the public repo — the key is injected at build time from a GitHub Actions secret.

Section 03

What this diagram does not expose

Sharing an architecture diagram is safe here — and this is why.

The Groq API key and the HMAC signing secret for access tokens both live in Cloudflare Worker environment variables — they are never sent to or cached in the browser. The resume data is encrypted with AES-256-GCM at build time; the decryption key is injected into the JS bundle by CI, never committed to source. Showing the flow reveals no exploitable secrets.

Section 05

DRAG — Distilled Retrieval-Augmented Generation

DRAG — Distilled Retrieval-Augmented Generation — trains a small 360M-parameter browser model to answer questions about this portfolio's content. A large teacher model generates grounded training data offline, then the student learns to extract and paraphrase from retrieved evidence via direct SFT.

flowchart TD KC[("Knowledge Chunks\nresume · companies · jobs")] subgraph DATAGEN["Stage 1 — Data Generation (local)"] direction TB DGS["gen-training-data.mjs\ngen-drag-data.mjs\ngen-graph-triples.mjs"] GROQ["Groq — Llama 3.3 70B\ngrounded Q&A generation"] GC{"Grounding Score ≥ 0.85"} JSONL[("Curated JSONL Dataset\n~460 examples")] DGS -->|"prompt each chunk"| GROQ GROQ -->|"candidate Q&A pair"| GC GC -->|"pass"| JSONL GC -->|"fail — discard"| DGS end subgraph SFT["Stage 2 — Direct SFT (Colab H100)"] direction TB STU["SFTTrainer — SmolLM2-360M\nbf16 · lr=2e-5 · completion-only loss · 8 epochs"] EVAL["Eval every epoch\nload_best_model_at_end=True"] STU --> EVAL end ONNX["optimum-cli ONNX export\nINT8 quantized"] HUB[("HuggingFace Hub")] COMP["Comparison Panel\nBase vs DRAG Fine-tuned"] KC --> DATAGEN JSONL --> SFT EVAL --> ONNX --> HUB --> COMP

The training data is the key: each example pairs a user question with a grounded answer generated by a 70B teacher model (Llama 3.3 via Groq API). The teacher sees evidence chunks and knowledge-graph triples, producing answers that are strictly traceable to source material. Examples scoring below 0.85 on grounding verification are discarded.

The student (SmolLM2-360M) trains on these curated examples using completion-only loss — prompt and evidence tokens are masked so the model's gradient budget focuses entirely on learning to generate accurate answers. Eval loss is tracked every epoch with early stopping to prevent overfitting on the small (~460 example) dataset.

Knowledge Chunks

The same encrypted JSON chunks the chat widget retrieves at runtime — resume, company context, and job postings — repurposed as training source material.

Groq Data Generation

Llama 3.3 70B (via Groq API) generates grounded Q&A pairs for the training dataset. Each answer is verified against source evidence — examples scoring below 0.85 are discarded.

Direct SFT

SmolLM2-360M trains directly on the curated Q&A pairs with completion-only loss. Eval loss is tracked every epoch; the best checkpoint is auto-selected to prevent overfitting.

ONNX INT8 Export

The fine-tuned checkpoint is exported to ONNX via optimum-cli --dtype fp32 --opset 18, then quantized to INT8 and pushed to HuggingFace Hub. Loaded in the browser with dtype: 'q8' via Transformers.js.
